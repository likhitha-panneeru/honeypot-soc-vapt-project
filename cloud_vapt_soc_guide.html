Cloud VAPT + Cloud SOC on AWS

Attack it. Log it. Detect it. Investigate it. This guide walks through standing up a deliberately vulnerable AWS app, turning on real cloud telemetry, attacking it like a pentester, and then investigating those attacks exactly the way a cloud SOC analyst would — end to end.

Why This Project

Most VAPT projects stop at the exploit. This one keeps going.

Every attack against a deliberately vulnerable AWS application is captured in real cloud telemetry, shipped to a SIEM, and investigated exactly the way a real cloud SOC analyst would. That's the whole idea in one sentence — you're not just breaking something, you're proving you can see the break happen, detect it, and respond to it.

Phase 1

Set up the AWS account and network

Before anything gets deployed, you need a place for it to live — an isolated network inside AWS, called a VPC (Virtual Private Cloud). Think of a VPC as your own private section of AWS's data center, walled off from every other customer's traffic.

1 Create/confirm your AWS account

Sign up at aws.amazon.com/free if you don't already have an account. A card is required for identity verification — a small refundable authorization is placed, no real charge if you stay in free tier.

2 Set your region

Pick a region close to you for lower latency — e.g. ap-south-1 (Mumbai). Every resource you create (EC2, VPC, GuardDuty) is tied to whichever region is selected in the top-right corner of the console.

3 Create a VPC

Console → search VPC → Create VPC → choose "VPC and more" (this auto-creates subnets, route tables, and an internet gateway for you). Give it a name like cloud-soc-vpc.

Inside that VPC, create:

  • One public subnet — where the Juice Shop web server will live, since it needs to be reachable from the internet for you to attack it.
  • One private subnet (optional) — for any logging component you don't want directly internet-facing. Not mandatory for a student build; skip if you want to move faster.
Why a VPC at all?
Every real AWS deployment lives inside a VPC — it's the fundamental unit of network isolation. Building one yourself (rather than using the account's pre-existing "default VPC") shows you understand network segmentation, which is core cloud security knowledge.

Phase 2

Launch the target EC2 instance

This is the server that will host Juice Shop — the deliberately vulnerable app you'll attack.

1 Launch an EC2 instance

EC2 → Launch Instance:

  • Name: juiceshop-target
  • AMI: Ubuntu Server 22.04/24.04 (Free tier eligible)
  • Instance type: t2.micro (Free tier eligible — enough for one Docker container)
  • Key pair: create new, download the .pem file, keep it safe
  • Network: place it in the public subnet of the VPC you just created
  • Storage: default 8GB is fine

2 Configure the Security Group (firewall)

Allow only what you actually need — this is different from a honeypot, where you want everything open. Here you want a realistic, minimal exposure:

  • Port 22 (SSH) — from your own IP only, not "Anywhere," since this is your management access, not a trap
  • Port 3000 (Juice Shop's web port) — from Anywhere (0.0.0.0/0), since this needs to be reachable to attack it like a real web app
Why lock down SSH but open port 3000?
A real production server only exposes the service it's meant to serve (the web app) — not its management interface. Restricting SSH to your own IP while leaving the web port open mirrors how a real, if imperfectly configured, web server would be set up. It's a small detail that shows security-minded thinking.

Phase 3

Deploy OWASP Juice Shop

Juice Shop is a deliberately, legally vulnerable web application built specifically for security practice. It's maintained by OWASP and contains dozens of intentional bugs — SQL injection, XSS, broken authentication, and more.

1 Connect to your EC2 instance

ssh -i your-key.pem ubuntu@YOUR_EC2_PUBLIC_IP

2 Install Docker

sudo apt update && sudo apt upgrade -y
sudo apt install docker.io -y
sudo systemctl start docker
sudo systemctl enable docker
sudo usermod -aG docker $USER

Log out and reconnect for the group change to apply.

3 Run Juice Shop

docker run -d -p 3000:3000 bkimminich/juice-shop

Downloads and starts Juice Shop, exposed on port 3000.

4 Confirm it's live

Open http://YOUR_EC2_PUBLIC_IP:3000 in a browser — you should see the Juice Shop storefront. This is now a legal, disposable practice target sitting on the real internet.

Phase 4

Turn on visibility — enable AWS's native security services

Right now, if someone attacks Juice Shop, nothing records it in a security-relevant way. This phase turns a plain EC2 box into a fully instrumented environment — every login, every packet, every scan leaves a trace.

CloudTrail＋ VPC Flow Logs＋ GuardDuty＋ Security Hub

1 Enable CloudTrail

Console → search CloudTrail → Create trail → apply to all regions → choose an S3 bucket to store logs (create a new one if needed).

What it captures: console logins, IAM changes, Security Group edits, EC2 start/stop — essentially every API call made against your AWS account.

2 Enable VPC Flow Logs

VPC console → select your VPC → Flow Logs tab → Create flow log → destination: CloudWatch Logs (simplest) or S3.

What it captures: source/destination IP, port, protocol, and whether traffic was allowed or denied — for every single connection to/from your VPC.

3 Enable GuardDuty

# Console: search "GuardDuty" → Enable GuardDuty
# No config needed — it starts analyzing automatically

What it captures: port scanning, brute-force attempts, unusual API calls, credential abuse — GuardDuty applies AWS's own threat-intelligence models against your CloudTrail and Flow Log data automatically.

4 Enable Security Hub

Console → search Security Hub → Enable. It automatically pulls in GuardDuty findings (and other AWS security checks) into one central dashboard.

Why all four, not just one?
Each covers a different layer: CloudTrail = "what changed in my account," VPC Flow Logs = "what network traffic happened," GuardDuty = "what looks malicious," Security Hub = "everything in one place." Together they turn a silent EC2 box into a fully observable system — this is genuinely how AWS-native security monitoring is built in real companies.
Cost note
GuardDuty includes a 30-day free trial per account per region. For a small student lab (low traffic, short duration), expect costs of well under $1-2 if you disable it right after your testing window. See the Cost & Safety section near the end of this guide.

Phase 5

Attack the target like a pentester

With telemetry now live, every action below will leave a trace somewhere in CloudTrail, VPC Flow Logs, or a GuardDuty finding — that's the entire point.

1 SQL Injection

Try classic login-bypass payloads against Juice Shop's login form, e.g.:

' OR 1=1--

If it logs you in without a real password, the app is vulnerable to SQL injection — a bug Juice Shop deliberately contains.

2 Cross-Site Scripting (XSS)

Inject a script into a vulnerable input field (e.g. the search bar):

<script>alert('XSS')</script>

If a popup fires, the app is reflecting your input back unescaped — a classic XSS vulnerability.

3 Brute Force

Run a controlled password spray against the login page using Hydra (from Kali):

hydra -l admin@juice-sh.op -P /usr/share/wordlists/rockyou.txt \
  YOUR_EC2_IP -s 3000 http-post-form \
  "/rest/user/login:email=^USER^&password=^PASS^:F=Invalid"

Simulates an automated credential-guessing attack — this generates repeated HTTP requests that VPC Flow Logs and GuardDuty will both notice.

4 Directory Enumeration

gobuster dir -u http://YOUR_EC2_IP:3000 -w common.txt

Scans for hidden pages/endpoints not linked from the main site — a standard early-recon technique real attackers use.

Why these four specifically
SQLi and XSS are the two most-cited entries in the OWASP Top 10 — almost every security interview touches on them. Brute force and directory enumeration represent the "automated/noisy" side of attacks, which is exactly what network-layer telemetry (Flow Logs, GuardDuty) is built to catch.

Phase 6

Ship the logs into a SIEM

CloudTrail, Flow Logs, and GuardDuty findings all exist natively inside AWS — but they're scattered across different consoles. A SIEM (Security Information and Event Management tool) pulls them into one searchable place, the way a real SOC analyst works.

Sources→ Staging (S3 / CloudWatch)→ SIEM (OpenSearch/ELK)→ Kibana Dashboards

1 Simplest path — CloudTrail → S3 → OpenSearch

CloudTrail already writes to an S3 bucket (from Phase 4). Use Amazon OpenSearch Service (AWS's managed Elasticsearch/Kibana) and set up an ingestion pipeline that reads from that S3 bucket.

Console → search OpenSearch Service → Create domain → choose a small free-tier-eligible instance type → once created, use OpenSearch Ingestion (or a Lambda function triggered on new S3 objects) to push CloudTrail records in.

2 VPC Flow Logs via CloudWatch

Since Flow Logs are already going to CloudWatch Logs (Phase 4), you can either subscribe a Lambda to forward them to OpenSearch, or use CloudWatch Logs Insights directly for simpler querying without a separate SIEM.

3 Lower-cost alternative — self-hosted ELK

If OpenSearch Service feels heavy for a student budget, run Elasticsearch + Logstash + Kibana yourself on a small EC2 instance (or Docker), and use Logstash's S3 input plugin to pull CloudTrail/Flow Log files directly. More manual setup, but avoids OpenSearch Service's hourly charges.

Why bother with a SIEM instead of just reading the AWS console?
In a real SOC, dozens of systems generate logs — nobody clicks through five separate AWS consoles during an incident. A SIEM correlates everything into one searchable timeline. Demonstrating this step, even at small scale, shows you understand how security operations actually function day-to-day.

Phase 7

Build the SOC console — dashboards and a detection rule

1 Kibana dashboards to build

DashboardWhat it shows
Top source IPsMost active external addresses hitting your app
Connections by portUnusual access attempts to web/admin ports
GuardDuty findingsActive AWS threat detections, listed and filterable
IAM activity timelinePrivileged or unusual API actions over time

2 Write an example detection rule

A simple threshold-based rule flagging high-volume requests to your app's port:

SELECT srcaddr, COUNT(*) as requests
FROM vpc_flow_logs
WHERE dstport = 3000
GROUP BY srcaddr
HAVING COUNT(*) > 100

Any source IP crossing 100 requests to port 3000 gets flagged — this is the same logic real SOC teams use for brute-force/scanning detection, just simplified.

3 Example resulting alert

ALERT: "Potential brute-force or scanning activity detected from 203.x.x.x." — this is what a GuardDuty finding or your custom Kibana rule would surface once your Hydra brute-force run (Phase 5) crosses the threshold.

Phase 8

The analyst workflow — when the alert fires

This is the sequence to actually practice and be ready to narrate in an interview — it's the core reasoning any SOC analyst performs on every alert.

1 Open the alert in Kibana

Start from wherever the finding surfaced — a GuardDuty entry or your custom detection rule firing.

2 Identify the source IP

Note the exact IP address associated with the suspicious activity.

3 Check all connections from that IP in VPC Flow Logs

Search Flow Logs for every connection from that address — how many requests, to which ports, allowed or denied.

4 Review GuardDuty findings for the same IP

Cross-reference — does GuardDuty independently flag this IP for port scanning, brute force, or something else?

5 Confirm the attack type

Based on the pattern (many failed logins = brute force; wide port sweep = scanning; single anomalous request = exploitation attempt), classify what actually happened.

6 Recommend containment

Document the recommendation: block the IP at the Security Group level, or add a WAF rule if one is in place.

Why this sequence matters
This exact reasoning chain — alert → source → correlate → classify → recommend — is what's discussed in SOC analyst interviews. Practicing it against your own real data means you can walk an interviewer through a genuine example, not a hypothetical one.

Phase 9 · Optional

Going further — two upgrades that raise the ceiling

1 Endpoint visibility with Wazuh

Install the Wazuh agent on your EC2 instance to correlate three layers of activity in one place:

  • Cloud activity — CloudTrail
  • Network activity — VPC Flow Logs
  • Host activity — Sysmon / Linux audit logs, captured directly on the instance

This turns the project into a hybrid cloud SOC — cloud-layer and host-layer visibility combined.

2 AI-assisted triage

A small Python script reads GuardDuty findings via the AWS SDK (boto3) and sends the finding text to an LLM, asking it to explain the threat in plain language and suggest containment steps.

Example output style:

AI-GENERATED FINDING SUMMARY
The EC2 instance is receiving reconnaissance traffic on an
exposed port — likely internet-wide scanning or targeted
probing. Restrict inbound access, enable AWS WAF, and review
connections from the source IP.

Safety

Cost & safety notes

  • EC2 t2.micro — free tier eligible, no cost if you stay within limits.
  • CloudTrail (management events) — free for the standard trail.
  • VPC Flow Logs — small CloudWatch storage cost, negligible at student-project volume.
  • GuardDuty 30-day trial — free for the first 30 days per account per region; after that, priced per volume analyzed. For a short, low-traffic student lab, expect well under $1-2 total if disabled promptly after testing.
  • OpenSearch Service free tier available — small instance types are free-tier eligible for the first 12 months; keep the domain small and short-lived.
Recommended safety routine
1) Set an AWS Billing Alert at a low threshold (e.g. ₹150-200) before enabling GuardDuty or OpenSearch.
2) Do all attack/testing in a short, focused window rather than leaving services running for weeks.
3) Disable GuardDuty and delete the OpenSearch domain immediately after capturing your screenshots and findings.
